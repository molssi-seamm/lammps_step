History#

2026.10.19 – Scale the charges of ions; LAMMPS in a parallel Loop was oversubscribed

  • The Initialization sub-step has a new option, ‘Scale the charges of ions by’, for the scaled-charge models of electrolytes (e.g. 0.8 for Li+ and BF4-): it multiplies the charge of every atom of each ion – each molecule with a net charge – by the factor. Neutral molecules are not changed, and a neutral salt stays neutral. The output lists the ions and their charges before and after, and md.h5md records the factor so that the analysis steps still find the ions.

  • Bugfix: in a parallel Loop each MPI rank of LAMMPS started as many OpenMP threads as the iteration had cores, since the Loop sets OMP_NUM_THREADS for the codes it runs: 4 iterations of 14 ranks on 56 cores ran 56 x 14 threads and made no progress. Every LAMMPS run now has one thread per rank (OMP_NUM_THREADS and MKL_NUM_THREADS = 1), as runs on GPUs and with QM engines already did.

2026.10.18.5 – Sample the mass fluxes of the species of a mixture with the heat flux

  • When the heat flux is sampled in a periodic system with more than one kind of molecule (by canonical SMILES, counting ions; up to 16), the momentum of each species is sampled with it, in species_flux.trj and in md.h5md as species_mass_flux. The Thermal Conductivity step needs them to remove the energy carried by the interdiffusion of the species, which made the thermal conductivity of mixtures too large. Nothing needs to be set.

2026.10.18.4 – Bugfix: runs on GPUs shared one CPU core

  • For runs on a GPU the step set OMP_PROC_BIND and OMP_PLACES, which made the OpenMP runtime bind each engine to the first CPU of the job as it started. The engines in a job then shared one core, so runs with a machine-learned forcefield were 2.5 to 3 times slower than they should be, and slower still with several runs at once, even on separate GPUs. The step no longer sets them; runs still use one OpenMP thread, and mdi_bind.sh and gpu_bind.sh bind CPUs where they can.

2026.10.18.3 – Internal: read the output files from disk

  • seamm-exec 2026.10.18 no longer reads the files a calculation returns into memory, since they can be gigabytes. The LAMMPS step now reads the ones it needs from the step’s directory, which works with earlier versions of seamm-exec too.

2026.10.18.2 – Bugfix: MD runs could use many times the memory of their output

  • After LAMMPS finished, the step formatted everything the run returned – the text of each sampled file – for a debugging message, whether or not it was logged. That took about nine times the size of the files: four runs at once of 1000 argon atoms, each writing 2 GB of centre-of-mass velocities, used about 10 GB each and brought down a 16 GB machine. Only the names and sizes of the files are logged now, and only when debugging.

2026.10.18.1 – Bugfix: runs in one allocation of several GPUs all used the first

  • Runs with a machine-learned forcefield started together in a Slurm allocation of several GPUs claimed different GPUs, as intended since 2026.10.17.3, but every engine still computed on the allocation’s first GPU, so they ran up to several times more slowly. The engine now sees only the GPU it claimed (mdi_bind.sh 2.4): its entry in the scheduler’s CUDA_VISIBLE_DEVICES, whether the scheduler counts the GPUs from 0 or uses the machine’s numbers. The new mdi_bind.sh replaces the old one in the installation’s bin at the first run, as before.

2026.10.18 – MDI over TCP as fast as MPI

  • MDI does not yet set TCP_NODELAY on its TCP connections, so each message could wait up to about 40 ms for the other side; for a fast machine-learned forcefield in an environment of its own, such as the default seamm-xnn, that could double the time of a step. On Linux, LAMMPS and the engine now preload a small library that sets it, compiled in the job’s directory with the machine’s C compiler, which makes TCP as fast as MPI. The same applies to quantum codes over MDI. Without a C compiler the run goes on as before, with a warning; tcp-nodelay = no in lammps.ini turns it off.

2026.10.17.3 – Bugfix: runs started together use different GPUs

  • Several LAMMPS runs with a machine-learned forcefield started at the same time on one machine – in one allocation of several GPUs, or by the task layer – all ran on the first idle GPU while the others sat idle. Each run now claims the GPU it uses for the length of the run, so the runs spread over the idle GPUs; only when every idle GPU is claimed do runs share one.

  • Over TCP, an engine whose LAMMPS never started – a wrapper in mlff-tcp-code that fails, for instance – waited for its connection for ever. It is now stopped after SEAMM_ENGINE_GRACE seconds (120 by default), and the run ends.

  • The output says whether the engine of a machine-learned forcefield has the fast paths it needs on a GPU, and warns when it lacks them (with xnn-step 2026.10.17.1 or later): without them a large system runs up to twice as slowly.

2026.10.17.2 – Bugfix: NPT of rigid models, and the first sample of every run

  • NPT dynamics of a rigid model such as SPC/E water stopped at once with “Fix shake must come before any box changing fix”: the SHAKE constraints are now set before the thermostat and barostat in NVE, NVT and NPT.

  • Bugfix: the first sample of each run’s time series is LAMMPS’s setup, at step 0, whose virial is not valid with constraints; pressures and stresses of up to 1e307 were written to md.h5md. The series now start at the first step of the dynamics.

  • md.h5md records the pressure an NPT run aimed at (it was left out), and the styles of the run’s fixes, so that the analyses know whether a run is isotropic.

  • Warnings from the analysis steps about the structure, e.g. that the system is small for them, are printed before the MD runs.

2026.10.17.1 – Bugfix: what the step says it does, and smaller jobs

  • The text of the Initialization sub-step said the van der Waals energies were shifted to zero at the cutoff whether or not they were, and never mentioned the tail correction; the input itself was right. Choosing a k-space method explicitly stopped the job with “KeyError: ‘method’”.

  • The description of a “normal”, “accurate but slow” or “coarse but fast” timestep read “a timestep of normal fs”; it now says how the timestep is chosen. The Velocities sub-step’s default no longer reads as if rotational momentum were removed from a periodic system.

  • The %CPU in the performance table was the first digit of LAMMPS’s value (9 for 97.9%), and the advice on the timing of the parts of LAMMPS ran words together and suggested balancing for uniform systems such as liquids, where uneven timing usually means the processors were shared with other work.

  • Citations: the Nosé–Hoover thermostat now cites Nosé, Hoover and Martyna, Klein and Tuckerman’s chains with the integrator, and NPT the barostat; the barostat paper is no longer cited for NVT runs.

  • The text files of the sampled positions and velocities are removed once they are in md.h5md (option “Keep the sampled text files”): they were most of the 6.4 GB of a 3 ns run of 1000 water molecules.

  • Ewald summation is chosen automatically only below 750 atoms (was 1000): for water PPPM is 1.4 times faster at 1000 atoms and 1.8 times at 3000.

2026.10.17 – The sampling an analysis needs, offered as a fix

  • When an analysis step after the MD (Viscosity, Diffusivity, Liquid Structure, Dielectric Constant, Ionic Conductivity, …) needs something the MD does not sample, the check before the job runs now offers to turn the sampling on in the MD sub-step: a button in the editor, or seamm-flowchart validate --fix.

2026.10.16.4 – The electrostatics method in the MD data

  • md.h5md records the run’s kspace style (e.g. ‘pppm 1.0e-5’, or ‘none’), for analyses whose formulas depend on it: the dielectric constant assumes Ewald or PPPM with conducting boundaries.

  • The output no longer fills with FutureWarnings from statsmodels about the autocorrelation functions of the summary properties.

2026.10.16.3 – Bugfix: rigid water was not held rigid in MD

  • In 2026.10.16.1 and 2026.10.16.2, NVE, NVT and NPT dynamics dropped the SHAKE constraints, so rigid models such as SPC/E water ran with flexible bonds and angles (the stiff harmonic terms that hold them in minimizations). Results of MD with rigid models from those two versions should be rerun; the shear viscosity of SPC/E water came out about twice too large. 2026.10.16 and earlier are not affected.

2026.10.16.2 – Bugfix: LAMMPS said it used more cores than it did; summaries are averages

  • In a batch job, LAMMPS can only use as many MPI processes as the job has tasks. A job with one task and several CPUs per task ran LAMMPS on one process, but the output said it was using all the cores the system’s size allowed. It now gives the number of processes LAMMPS actually runs on, and when the job’s allocation is what limits it, explains that MPI processes need tasks (e.g. –ntasks) rather than CPUs per task.

  • The summary of an NVE, NVT, NPT or Heat Flux run (<ensemble>_summary.trj), ten lines over the run, now gives on each line the average over that tenth of the run, sampled every 10 steps, rather than the values at that one step.

2026.10.16.1 – Extra commands and extra properties in the MD sub-steps

  • The NVE, NVT and NPT sub-steps have an Extras tab. Extra commands are LAMMPS compute, fix, variable and dump commands for that sub-step only, removed when it ends. Extra properties are LAMMPS expressions, each with a name and units, sampled and analysed with the built-in properties, as an average, an autocorrelation function with its correlation time, or a Green-Kubo integral with a chosen prefactor. They are printed, graphed, written to md.h5md as observables/user/<name>, and can be stored as properties of the configuration.

  • Mistakes in the extra commands or properties are shown in the dialog as they are typed, and stop a job before it runs.

2026.10.16 – Rigid models from the forcefield, and the heat flux of liquids corrected

  • Which bonds and angles are rigid now comes from the forcefield, e.g. the SPC/E and TIP3P water in the new forcefields oplsaa+-spc_e and oplsaa+-tip3p, and SHAKE holds exactly those. Before, any water was made rigid, whatever the forcefield; a flexible water model such as oplsaa+’s SPC is now flexible.

  • A rigid bond or angle is also a stiff harmonic term, so that minimizations, which cannot use SHAKE, keep the geometry.

  • Bugfix: the Heat Flux sub-step turned SHAKE on only after the runs that settle the system and average each atom’s energy and stress, so rigid water ran unconstrained there and the run failed after a few femtoseconds.

  • Bugfix: when LAMMPS stopped with an error in the Heat Flux sub-step, the job hung instead of stopping.

  • Bugfix: the Heat Flux sub-step subtracted each atom’s average energy and stress from the heat flux. That is right for a crystal, but in a liquid, where the atoms move, it made the thermal conductivity too large, by about 20% for SPC/E water. By default the heat flux is no longer filtered; the new “Filter the heat flux” can still subtract the per-atom averages, for solids. Without the filter, Heat Flux is a plain LAMMPS run with no preliminary runs.

  • Bugfix: the heat flux of the NVE, NVT and NPT sub-steps left out the forces holding rigid bonds and angles, and in NVT and NPT counted the convective term twice. Both are corrected, and the computes they define are removed afterwards, so a later sub-step can sample the heat flux again.

2026.10.15.4 – Bugfix: rigid water gave the wrong pressure

  • Rigid water molecules, and fixed X-H bond lengths, were held with LAMMPS’s RATTLE, which for rigid SPC/E water gave a pressure about 850 atm too high, an anisotropic pressure tensor and a center of mass that drifted ever faster, so the viscosity and diffusion coefficients were wrong. SHAKE is now used, with a tolerance of 1e-6, which gives the right pressure and conserves momentum.

2026.10.15.3 – Sampling the full pressure tensor, for the viscosity

  • The NVE, NVT and NPT sub-steps can sample the full pressure tensor often, as the viscosity needs, with “Sample the pressure tensor”. It replaces “Sample the shear stress”, which saved only the three off-diagonal components; flowcharts that used it now sample the full tensor.

  • The sampled pressure tensor is written to md.h5md as pressure_tensor, in place of the coarser one from the thermodynamic state, and analysis steps such as Viscosity can ask for it to be turned on.

  • Bugfix: “Keep the internal geometry of water molecules fixed”, on by default, did nothing since 2020, so water was always flexible. Water molecules (an O bonded to two H’s) are now held rigid with RATTLE.

  • Bugfix: “Fix X-H bond lengths” in the Initialization sub-step looked up the elements of the wrong atoms, so it stopped with an error or constrained the wrong bonds.

  • Bugfix: the nacl_water forcefield, with SPC/E water and ions, could not be used: LAMMPS stopped with “Special bonds not implemented”.

  • Requires seamm-md-analysis 2026.10.15.2.

2026.10.15.2 – Analysis steps can check and adjust the MD before it runs

  • The NVE, NVT, NPT and Heat Flux sub-steps tell analysis steps what each run will sample, before it runs, and can turn on sampling an analysis needs.

  • Just before LAMMPS runs, the analysis steps that will read its MD check the structure, so that, for example, Diffusivity stops the job before the MD if the system is not periodic.

2026.10.15.1 – The MD data in H5MD files; non-periodic systems

  • At the end of each NVE, NVT, NPT and Heat Flux sub-step, everything the run sampled is written to md.h5md in the sub-step’s directory: the time series, the full pressure tensor, the trajectory and centres of mass with the box of each frame, and the run’s parameters and provenance. The analysis steps read it. LAMMPS’s own files are still written and kept.

  • Each MD run is recorded in the variable _md_runs.

  • Bugfix: sampling the trajectory of a non-periodic system (a molecule or cluster) failed with “Variable name sxx … does not exist”. For a non-periodic system the pressure is no longer reported, the heat flux and shear stress are not sampled (with a warning), and the Heat Flux sub-step stops with a clear message.

2026.10.15 – Bugfix: the heat flux was far too large

  • The Heat Flux sub-step removes each atom’s average energy and stress from the heat flux, to reduce its noise. The stress was handed to LAMMPS in the wrong units and with the wrong sign, which changed it by 68,568 times its average instead of removing it. For liquid argon the heat flux was about 10,000 times too large and the thermal conductivity about 4x10^7 W/m/K; it is now about 0.1 W/m/K, as measured. Every thermal conductivity computed with the Heat Flux sub-step for a system without bonds (e.g. with class II forcefields such as PCFF) was affected.

  • For molecular systems the average stress was not removed at all, and the convective part of the heat flux was counted twice. Both are corrected, also for the heat flux sampled during NVE dynamics.

  • The Heat Flux sub-step sampled the heat flux 1000 times per run, e.g. every 20 fs for a 20 ps run. That is too coarse for the fastest vibrations, which then alias into the Green-Kubo integral: for liquid water the thermal conductivity came out 3-4 times too large. The heat flux is now sampled every two timesteps, and the meaningless “50” for the heat flux sampling is no longer shown in the dialog. For water the thermal conductivity is now about 1 W/m/K.

  • After the Heat Flux sub-step the final coordinates and velocities were not read back into the configuration, because the step looked for a file of the wrong name. They are now.

2026.10.14.1 – Bugfix: MLFF dynamics on the CPU, NVE run length and short runs

  • A machine-learned forcefield from the Model Chemistry step now runs on the CPU when the job can have no GPU, using the job’s cores less one for LAMMPS. Before, the step either waited forever for a GPU or stopped with “PyTorch forcefield requested, but no GPUs!”. The Forcefield step’s PyTorch models still need a GPU.

  • With busy GPUs the step waits for one for --gpu-wait-time seconds; a finite wait never ended before.

  • NVE dynamics with a machine-learned forcefield, or any model in LAMMPS’s metal units, ran 1000 times the steps asked for (e.g. 40,000 steps for 0.02 ps at 0.5 fs). NVT and NPT were right.

  • Dynamics of fewer than 100 steps (NVE, NVT, NPT, Heat Flux) stopped with “Illegal fix ave/time nfreq value: 0”.

  • Files the MLFF engine writes, such as a committee’s spreads, are now kept rather than removed when the run finishes.

2026.10.14 – Bugfix: machine-learned forcefields with the engine in its own environment

  • A machine-learned forcefield from the Model Chemistry step failed on a default installation (“xnn: not found”): its engine and LAMMPS were always run as an MPI pair in LAMMPS’s environment, which works only when one environment holds both, as on a cluster set up that way. When xnn.ini names another environment, the engine now starts there with conda run and the two talk over TCP on the same machine. mlff-transport in lammps.ini (auto, mpi or tcp) overrides the choice and mlff-tcp-code changes the LAMMPS command. On Linux TCP is currently slower than MPI, by about a third for a fast model, until the MDI library sets TCP_NODELAY (proposed upstream).

  • mdi_bind.sh 2.3 runs a pair started without mpirun: SEAMM_MDI_ROLE names each side and SEAMM_MDI_PAIR the pair. Stopping a partner also stops its child processes, such as an engine started by conda run.

  • The helper scripts in <root>/bin (mdi_bind.sh, cpu_bind.sh, gpu_bind.sh, mdi_monitor.sh) are now upgraded when the plug-in ships a newer version, keeping the old copy as, e.g., mdi_bind.sh.2.2; before, the step only logged a warning that was easy to miss, and old copies failed (mdi_bind.sh 1.3 does not run with macOS’s bash). A job running the old script is not affected. A script without a #MolSSI header line is left alone.

2026.10.12.1 – Machine-learned forcefields from the Model Chemistry step

  • LAMMPS can take a machine-learned forcefield (xnn:MLFF@...) from a Model Chemistry step, with its checkpoint and engine options, and runs its engine and LAMMPS as an MPI pair on a GPU, each through mdi_bind.sh – as gpu-code in lammps.ini did for the Forcefield step’s PyTorch models, which still works. mlff-code in lammps.ini can change the launch. Requires xnn-step 2026.10.12 and model-chemistry-step 2026.10.12.1.

2026.10.12 – Forcefields from the Model Chemistry step

  • LAMMPS can take its forcefield from a Model Chemistry step: FF@oplsaa, ReaxFF@CHO_cho_2008 and the others the Forcefield plug-in offers. It builds the forcefield and types the atoms as it does with the Forcefield step, which still works as before. A model chemistry with a quantum method still runs the dynamics with the program over MDI.

  • Requires forcefield-step 2026.10.12.1 and model-chemistry-step 2026.10.12.

2026.10.11.2 – Bugfix: mdi_bind.sh 2.2 really stops a failed MDI pair

  • 2.1 did not end a failed MLFF run. LAMMPS does not exit after an error in an MDI pair – it waits in MPI_Finalize for the engine – so neither side ever exited; and stopping a partner stopped only the shell around it, leaving the program running. 2.2 starts each program with exec, so that stopping it stops the program, and watches a copy of LAMMPS’s output for ERROR lines: if LAMMPS has not exited SEAMM_ERROR_GRACE seconds (default 30) after one, it is stopped, and with it the engine. Tested on TinkerCliffs with LAMMPS and an xnn model: a failed run now ends within a minute instead of holding its GPU until cancelled.

  • The driver’s output passes through unchanged, and line-buffered as it is on mpirun’s terminal, so a hung LAMMPS no longer loses its output.

2026.10.11.1 – Bugfix: a failed LAMMPS run no longer leaves its MDI engine holding the GPU

  • In an MDI pair (e.g. a machine-learned potential driving LAMMPS) a LAMMPS error left the engine waiting for its driver forever: the job held its GPU and stayed RUNNING until cancelled. mdi_bind.sh (version 2.1) now stops the engine when the driver fails, and the driver when the engine fails; after a normal finish the engine has SEAMM_ENGINE_GRACE seconds (default 120) to exit.

  • Installing the step does not replace an existing ~/SEAMM/bin/mdi_bind.sh; the step warns that a newer version is available. Replace it by writing the new file beside it and renaming it over the old one, so that running jobs keep their copy.

2026.10.11 – The step declares what its cost model is made of

  • lammps.TIMING_SPEC – atoms as the size variable, the forcefield as the class, and MD steps as the unit – is passed with each timing record (seamm-exec 2026.10.6.1 and later write it beside the records), so the cost model is fitted from the step’s own description.

  • Each timing record names the forcefield (its form – PyTorch, OpenKIM, MDI/QM or a classical form – and the model or checkpoint), so that machine-learned and classical forcefields, orders of magnitude apart in cost, are fitted separately; a run on a GPU also records the GPU’s model.

  • Removed the Docker image (and its recipe and release job) and the Docker settings in the default lammps.ini, which were no longer used or maintained.

  • Requires Python 3.12 or later.

2026.10.6.1 – Bugfix: forcefield runs failed after LAMMPS finished

  • 2026.10.6’s timing record used a variable bound only for QM-MD over MDI, so every ordinary forcefield run raised UnboundLocalError once LAMMPS had finished and its results were never analyzed (ChemAI jobs 5177-5188). The record now takes only what every run has.

2026.10.6 – Timing records that a cost model can be fitted to

  • Each LAMMPS run appends a record to ~/.seamm.d/timing/lammps.csv through seamm_exec.timing: the machine class, processes, wall time and outcome, and the descriptors of the calculation: the sub-steps run, the structure, and from the log the Loop time lines: MD steps, atoms, processes and LAMMPS’s own time (steps times atoms is the unit of cost). This replaces the step’s own CSV (SMILES, formula and the whole parameter dictionary as JSON), which grew without bound. See seamm_exec’s campaign of 2026-10-05.

  • Requires seamm-exec 2026.10.6.

2026.10.5 – Job-level files for parallel loops

  • Files named /name are written to the job’s own directory (Node.job_path) and read from it or, in an iteration of a parallel loop (loop_step 2026.10.5), from the enclosing iterations and the job. Nothing changes for other jobs.

  • Requires seamm 2026.10.5.

2026.10.3 – Bugfix: QM/MD over MDI used the program’s method name and default basis

  • The MDI engine for a QM-driven LAMMPS run was launched with the model chemistry’s method name alone, so ORCA ran def2-SVP whatever basis was chosen, and a functional whose name the Model Chemistry step had to alter was not recognized. It now gets the program’s own keyword and the chosen basis (with model_chemistry_step 2026.10.3).

2026.10.1 – Settings that depend on each other; LAMMPS errors reported

  • The dialogs show only the settings that apply with the current choices, and SEAMM’s flowchart tools use the same rules. Settings that were hidden but used now apply where they matter: the charged-atom threshold whenever there is a k-space method; the QEq settings for the forcefield’s default charges; the damping times for the Berendsen barostat too. Allow shear applies only to a solid with the Nose-Hoover barostat.

  • A Berendsen NPT step whose box must be triclinic failed inside LAMMPS; it is now refused before LAMMPS starts, saying why.

  • Bugfix: when LAMMPS itself stopped with an error, the step failed later with an unrelated IndexError. It now stops with LAMMPS’s message, the sub-step, the last command, advice for common errors, and where the log is.

  • Bugfix: an explicitly chosen k-space method raised KeyError; Minimization read Sxy from Sxz; NPT’s stress damping times were converted as pressures, and with y and z coupled z’s final stress was wrong; NPT’s mtk and nreset were not used; Velocities’ default momentum choice was not one of its own choices.

  • Documented in the user guide. Needs seamm 2026.10.1.

  • Internal: CI now installs the package’s declared dependencies with uv rather than a conda test environment; model-chemistry-step, which it uses, is now declared.

2026.9.29 – Bugfix: the CPU/GPU binding scripts work on any machine

  • mdi_bind.sh, gpu_bind.sh and cpu_bind.sh bound the codes to fixed CPU cores laid out for one machine (an AMD EPYC 7763 with two GPUs). Elsewhere they failed: under SLURM or another scheduler, when the job’s cores were not those (“taskset: failed to set pid’s affinity: Invalid argument”); on a third or later GPU (“no CPU binding defined for GPU 2”); and on machines with fewer cores. On other layouts they silently pinned to unrelated cores.

  • Version 2.0 of the scripts works the binding out from the machine. Under a scheduler (SLURM, PBS, LSF) it leaves the binding to the scheduler. Otherwise it uses the CPUs next to the GPU, from nvidia-smi topo -m, limited to the CPUs the job may use; GPUs sharing those CPUs split them, and the engine and LAMMPS take halves. If none of that can be determined the code runs unbound rather than failing. SEAMM_BIND=none turns binding off, and SEAMM_ENGINE_CPUS/SEAMM_DRIVER_CPUS (SEAMM_CPUS for cpu_bind.sh) choose the CPUs by hand.

  • The scripts also find the MPI rank under MPICH and srun, not only OpenMPI, and gpu_bind.sh no longer overrides a GPU allocation the scheduler made.

  • The warning that a newer version of a helper script is available never appeared, because its version header was misread; it does now. The copies in ~/SEAMM/bin are not replaced automatically, since they may have been edited: delete an older mdi_bind.sh, gpu_bind.sh or cpu_bind.sh to get version 2.0, unless you tuned it for your machine.

  • The documentation and the lammps.ini examples now give the plain command for an MDI engine (mpirun --bind-to none -np 1 <engine> : -np 1 lmp), which works on workstations and clusters alike, with mdi_bind.sh as an option.

2026.9.25 – Bugfix: the LAMMPS step failed to load on Python 3.12 outside conda

  • The step used the GPUtil package to find idle GPUs. GPUtil is unmaintained and imports distutils, which was removed from Python 3.12, so in any environment without setuptools (a plain venv, for example) the LAMMPS step silently failed to load and was missing from the flowchart editor. It worked in conda environments only because conda installs setuptools everywhere. GPU detection now queries nvidia-smi directly and GPUtil is no longer a dependency.

2026.9.20 – Bugfix: a large system could be given a net charge

  • The charges were written to the structure file for LAMMPS with three decimals, while a forcefield assigns four or more. For a small molecule the rounding is harmless, but over a large system it accumulates: 500 molecules of ethylene carbonate, 5000 atoms whose charges add up to zero, were handed to LAMMPS as a system with a charge of -1. They are now written with six decimals, which leaves the total as the forcefield set it.

  • Warnings from assigning the forcefield – in particular that the charges did not add up and have been adjusted – now appear in the step’s output and the job’s output. They went only to the log, which for a job in a queue is the queueing system’s output file if it is kept at all, so a change to the charges could pass unnoticed.

  • Internal: pinned bibtexparser to 1.x and added Pmw in the test environment, both of which the tests need and neither of which was there.

2026.9.16 – Bugfix: trajectory output failed with machine-learned potentials

  • Writing a trajectory (dump or extxyz) from a run using a PyTorch/MDI potential such as MACE died in LAMMPS with “Unknown dump_modify keyword: H”. The element list given to LAMMPS had one entry per atom rather than one per atom type, so for anything beyond a handful of atoms the surplus entries were read as keywords. The list is now per type, as it already was for OpenKIM models.

  • The Python engine for ML potentials has been renamed from xnns to xnn. The examples in the default lammps.ini and comments now use the new name. If your ~/SEAMM/lammps.ini has a gpu-code line using xnns mdi, change it to xnn mdi and reinstall the engine, since checkpoints saved with the new package can only be loaded by it.

2026.9.15.2 – Bugfix: concurrent GPU jobs bound to the same cores

  • mdi_bind.sh chooses which cores to run the engine and the driver on from a map of the GPUs on the machine, so that each is near its card. It was looking that map up by the GPU’s index within the job’s own allocation, which is 0 for every job given a single GPU whichever card that is, so two jobs running at once both took the cores belonging to GPU 0 and shared them. It now looks up by the physical index, and jobs on different cards get different cores.

  • Note that ~/SEAMM/bin/mdi_bind.sh is not replaced once it exists, since the core layout in it is specific to the machine and meant to be edited. Delete it to pick up this version.

2026.9.15.1 – Machine-learned forcefields are served by an engine, whichever one

  • Which engine evaluates a machine-learned forcefield is now set entirely by gpu-code in lammps.ini. The model file is offered to it two ways – as the SEAMM_FF environment variable, and as {MODEL} for substitution into the command – so an engine taking the model as an argument, such as ‘xnns mdi –ckpt {MODEL}’, works alongside one reading the environment, such as mace-mdi, with nothing in the plug-in needing to know which is configured.

  • Every PyTorch forcefield except an ML-IAP one now goes to that engine. The choice used to depend on the model file being named ‘.mace.pt’, with anything else falling back to ‘pair_style mace’. A file name says nothing about how a model is evaluated, and reaching that pair style needs a LAMMPS built with it – which is the build the MDI route exists to avoid needing. A checkpoint named for what it was rather than for that convention failed with “Unrecognized pair style ‘mace’”. The pair style is no longer written.

  • The comm_modify line an MDI run needs was applied on the same file-name test, so it now applies to every MDI run.

2026.9.15 – Bugfix: a classical forcefield was sent to the machine-learning engine

  • Asking for a GPU made any LAMMPS job take the GPU command from lammps.ini, whatever the forcefield. Where that command launches an MDI engine – the usual setup for machine-learned potentials – a classical run such as OPLS-AA was handed to that engine, which has no model to serve and died with “FileNotFoundError: ‘Unknown’” before LAMMPS ran at all. The GPU count comes from the scheduler, so it says nothing about what the calculation needs; the choice now depends on whether the configured command suits the forcefield. A Kokkos GPU command, which is how a classical forcefield is meant to use a GPU, is unaffected.

  • This only became reachable when queues began offering a GPU count at submission, so the first classical job submitted with one hit it.

2026.9.14.3 – Say plainly when a GPU job has too few tasks

  • A GPU command that drives an MDI engine runs the engine and LAMMPS as separate MPI ranks, and those counts are written into the command rather than derived from the allocation. A job given fewer tasks than the command asks for died inside mpirun with “All nodes which are allocated for this job are already filled”, which mentions neither MDI, nor tasks, nor what to change – and arrived wrapped in a conda error, obscuring it further. The step now checks before launching and says how many tasks the command needs, how many the job was given, and that an MDI run needs one task for the engine and one for the driver.

  • This is easy to hit now that queues can offer a GPU count at submission: requesting one GPU and one task looks reasonable but cannot work.

2026.9.14.2 – Bugfix: could run on a GPU the scheduler had not allocated

  • When choosing GPUs the step asked GPUtil, which reads nvidia-smi and therefore reports physical GPU indices, knowing nothing about CUDA_VISIBLE_DEVICES. A scheduler that allocates a subset of a node’s GPUs sets that variable, which also renumbers the devices: given physical GPU 1, a job’s own device 0 is that GPU. The step would report GPU 1, so the calculation could run on a card it had not been given, alongside whichever job actually held it. GPUs are now selected in the numbering CUDA itself uses, and a GPU outside the allocation is never chosen.

  • mdi_bind.sh no longer overwrites CUDA_VISIBLE_DEVICES when a scheduler has already set it. That variable is not composable – setting it again is interpreted against the machine’s full set of devices, not against the allocation – so overwriting it was another way to land on the wrong GPU. The GPU monitor still logs the physical card, mapped back for the purpose.

  • Both only affected machines where a scheduler hands out individual GPUs. Where every job sees every GPU the behaviour is unchanged.

2026.9.14.1 – Internal: the MACE MDI engine is no longer duplicated here

  • This plug-in shipped its own copy of the MACE MDI engine as mace_mdi.py and installed it into ~/SEAMM/bin. The same engine is maintained in the lammps-mdi package, and the two had drifted well apart: the bundled copy was missing, among other things, the fix for loading a GPU-saved model on a machine without a usable GPU. It has been removed, and the example configurations now use ‘mace-mdi’, the console script from lammps-mdi.

  • An existing ~/SEAMM/bin/mace_mdi.py is left in place, so a configuration pointing at it keeps working. The step now warns when gpu-code still refers to it, since that copy no longer receives fixes.

  • Note that lammps-mdi is deliberately NOT a dependency of this plug-in: it pulls in PyTorch and MACE, which belong in the LAMMPS environment rather than the SEAMM one. The Getting Started guide shows how to install it there.

2026.9.14 – Bugfix: machine-learned forcefields could not run at all

  • The conda environment asked for conda-forge’s LAMMPS, which is built without the MDI package. Since machine-learned forcefields are run by driving a separate engine over MDI, they could not work: LAMMPS rejected the ‘-mdi’ option and then hung until the job hit its time limit rather than reporting the error. The environment now uses an MDI-enabled LAMMPS, and OpenMPI, so that LAMMPS and the engine share one MPI and one MDI library.

  • PyTorch and the MACE stack are deliberately not part of that environment, as the correct PyTorch build depends on the machine’s NVIDIA driver. Install them with ‘lammps-mdi install-ml’, which works this out for you. The Getting Started guide now covers setting up a machine-learned forcefield end to end.

  • Fixed mdi_bind.sh reporting failure after a run that had in fact succeeded, which made a completed MDI calculation look like a failed one. Note that an existing ~/SEAMM/bin/mdi_bind.sh is not replaced automatically, since it is meant to be edited; delete it to pick up the fixed version.
